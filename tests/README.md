# Tests

The test layers follow `TESTING.md` section 2.

| Directory      | Layer                  | Runs in                 | Content                                                              |
| -------------- | ---------------------- | ----------------------- | -------------------------------------------------------------------- |
| `fixtures/`    | Test data              | —                       | Synthetic input files, generated by `scripts/generate-fixtures.mjs`. |
| `integration/` | Rust and process level | `cargo test`, CI        | Real conversions against real fixtures, output validation, cleanup.  |
| `e2e/`         | Application level      | Manual, later automated | Adding files, starting and cancelling a job, reading the result.     |
| `quality/`     | Reports                | Manual                  | Conversion duration, peak memory and validation results per run.     |

## Current state

The domain layer is covered by the Rust test suites:

- `crates/ufc-core/src/domain/*.rs` — unit tests next to the code they
  cover.
- `crates/ufc-core/tests/job_state.rs` — the job state machine
  through the public API.
- `crates/ufc-core/tests/capability_registry.rs` — the rule that only
  implemented pairs with an available engine are offered.
- `crates/ufc-core/tests/error_contract.rs` — the error wire format
  that the frontend depends on.
- `src/**/*.test.ts` — frontend unit and component tests.

`integration/`, `e2e/` and `quality/` stay empty until a conversion
pair exists. Filling them with placeholder tests would only pretend
that a conversion works.

## Fixtures

Fixtures are generated, not committed:

```bash
node scripts/generate-fixtures.mjs
```

The generator writes into `fixtures/generated/`, which is ignored by
git. Synthetic files keep the repository free of third party content
and make every fixture reproducible.

See `fixtures/README.md` for the list of fixtures and what they are
used for.
